Agent support during deterministic service journeys

RFC discussion

Agentic Legibility

2026-07-15

What is the agent for?

  • The executor controls the journey.
  • The agent supports the current step.

Why this matters

How do we not just fill in a form in a chat window? The agent can help by using:

  • earlier conversation
  • structured user data
  • corrections and conflicts
  • journey questions
  • approved retrieval tools

Proposed decision

Agree that the agent supports the journey through bounded structured actions.

The executor remains responsible for:

  • form rendering
  • validation
  • confirmation
  • branching
  • submission
  • outcomes

The agent recommends support for the current step.

Proposed agent actions

Action What it means
Propose values Fill fields with candidate values
Surface conflict Show competing plausible values
No safe suggestion Decline to populate fields
Retrieve information Look up approved supporting information
Flag inconsistency Highlight inconsistent in user response
Answer journey question Explain the active journey
Prompt to exit or continue Handle a separate request

These are desired capabilities, not necessarily the first implementation scope.

Example: propose values

{"current_step": "enter_new_address"}

Conversation history: I recently moved to 18 Station Road, Bristol, BS1 3AB

Expected action:

{
  "actions": [
    {
      "type": "propose_values",
      "values": {
        "address_line_1": "18 Station Road",
        "town_or_city": "Bristol",
        "postcode": "BS1 3AB"
      }
    }
  ]
}

The executor shows fields for review and confirmation.

Example: surface conflict

My new address is 18 Station Road, Bristol, BS1 3AB.
Later: Please use 81 Station Road, Bristol, BS1 3AB.

The agent should not guess.

{
  "actions": [
    {
      "type": "surface_conflict",
      "field": "new_address",
      "candidates": ["18 Station Road", "81 Station Road"]
    }
  ]
}

Example: no safe suggestion

My sister lives at 18 Station Road, Bristol, BS1 3AB.

The address is complete.

But it is not the user’s address.

Expected action:

{
  "actions": [
    { "type": "no_safe_suggestion" }
  ]
}

Decision 1: beyond the API surface to answer_journey_question

I’m staying with my sister for a few months. Should I use her address as my new address?

  • The API tells us which field is required, but not how to explain it.
  • There is a value in an agent at this point.
  • Does an agentic transaction require access to guidance beyond the transactional API?

Decision 2: how far should retrieve_information go?

My address is 18 Station Road, BS1

Possible sequence:

This could be much better than asking the user to type the full address again.

Decision 2: how far should retrieve_information go?

Narrow retrieval

  • address lookup
  • service-specific guidance
  • known structured data

Broader retrieval

  • GOV.UK content search
  • departmental APIs
  • approved web sources

Retrieval may support both form filling and question answering.

Decision 3: how far should flag_possible_inconsistency go?

Example What is needed
User enters address chat history suggests is mistaken Journey guidance defining the field
Postcode does not match street Address lookup or validation service
Address valid but outside scope of the service Service rules or deterministic validation
Dates overlap or appear in an impossible order Deterministic rules or calculation
Vehicle registration not associated with user Departmental API or authoritative data
Sum of tax form’s amounts don’t equal total Calculation rather than a knowledge base
  • Do not replicate departmental validation.
  • Scope should be limited to information from Chat.
  • Decision is: does this generate any more requirements for departments than retrieve_information?
