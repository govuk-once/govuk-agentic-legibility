Agentic Legibility: Journey Search Prototype

Service Legibility

Journey Search: an MCP server and an evaluation suite

Two things you can use now, to see whether the orchestrator can find the right government service for a citizen without already knowing the catalogue.

1 tool

A hosted MCP server

search_service_journeys returns a shortlist of candidate GOV.UK Forms from a catalogue of about 550. Connect with OAuth client credentials.

Evaluation scenarios

Citizen messages with expected outcomes, for you to run against the orchestrator.


Design principle: The orchestrator decides when to search but does not know which service journeys exist. Search should be a lightweight, low-latency tool that can be used frequently, to avoid missing journeys.

Where it fits

Journey Search retrieves. The orchestrator decides.

Citizen

Talks only to the orchestrator.

⇄conversation

GOV.UK orchestrator

The agent owns the conversation, has other tools, and decides whether to search, what to search for, and what to do with the results.

⇄MCPsearch_service_journeys

Journey Search

Our MCP server. Stateless. Returns ranked candidates, each with an ID, title and description.

After a search, the orchestrator can…

  • offer the one journey that fits
  • ask the citizen which of several applies
  • search again with a better query
  • decide none fits and use another capability

Things to know

  • Candidates are not necessarily matches. It always returns up to limit, even when nothing fits.
  • Searching doesn't start anything. Starting a journey is a separate call, after the citizen agrees.
  • No state between calls. Put what matters from the conversation in the query.

The MCP tool

One call: a plain-language query in, candidates out

search_service_journeys(
    query: str,      # plain words
    limit: int = 5,  # up to 20
)
  • The citizen doesn't need to know the service's name.
  • Don't put personal details in the query.
  • The tool description, which the model sees, explains how to judge results.
  • About 300 ms per search on an open connection.

					

				

			

		

	


	
	

		

			
Connecting

			
Five settings, then add it to the agent's tools

			

				

					
1. Get credentials from us

					
JOURNEY_SEARCH_MCP_URL
JOURNEY_SEARCH_TOKEN_URL
JOURNEY_SEARCH_CLIENT_ID
JOURNEY_SEARCH_CLIENT_SECRET  # sent separately
JOURNEY_SEARCH_SCOPE

					
OAuth client credentials. You don't need access to our AWS account.

					
2. Check access

					
uv run strands_client.py tools
uv run strands_client.py search "report a mosquito"

				

				

					
3. Use it from Strands (or any MCP client)

					
journey_search = MCPClient(
    url=os.environ["JOURNEY_SEARCH_MCP_URL"],
    auth_provider=JourneySearchAuth(),  # bearer token
)

with journey_search:
    agent = Agent(
        model=your_model,
        tools=journey_search.list_tools_sync()
              + your_other_tools,
    )

					
Streamable HTTP with Authorization: Bearer <token>. The full
						auth class, a curl example and error codes are in
						forms_search/journey_search/CONNECTING.md.

				

			

		

	


	
	

		

			
The backend

			
Tech stack

			

				
Orchestrator
Any MCP client with streamable HTTP.

				
→HTTPS +
Bearer token

				
AgentCore Runtime
Amazon Bedrock AgentCore. Its JWT authoriser checks the
					Cognito token first.

MCP container
Python, MCP SDK (FastMCP). ARM64 image. Stateless.

				
→

				
Retrieval
Bedrock: embed the query with Cohere Embed v4
					(1,536 dims).
DynamoDB: vector index (cosine), queried with SearchVectors.

The evaluation suite

			
 scenarios, each with one expected outcome

			

			

				

					
offer_journeyThe agent offers this specific workflow ID. Merely being returned by search doesn't count.

					
clarifyThe agent asks a relevant question instead of committing to a journey.

					
no_journeyThe agent offers no Form. Answering normally or using another tool is fine.

				

				

					
Each scenario also says whether search is required or forbidden,
						at any point in the conversation.

					
 scenarios have two turns: the first is ambiguous, and a scripted second message
						resolves it.

					
Synthetic, for checking the architecture. Not a sample of real citizen traffic.

The evaluation suite

			
Running it against the orchestrator

			

				
    
					
  1. Start a fresh conversation per scenario and send only the user text. Never show the agent the expected outcome.
    2. 
					
  2. Let it decide whether to search, what for, and how many times.
    3. 
					
  3. Record which workflow ID it offered, for example a structured decision or an unconfirmed "start journey" call, plus every search and its candidates.
    4. 
					
  4. For two-turn scenarios, send the second message only if it clarified.
    5. 
					
  5. Score each turn and the search rule. Pass only if all hold.
    6. 
				

				

					

						
What we'd like back

						
    
							
  • Pass rates by category, so the large catalogue group doesn't hide the rest
    • 
							
  • Traces, so each failure can be put down to the dataset, the search tool or the orchestrator
    • 
							
  • Whether the expected ID was retrieved at all, separately from whether it was offered
    • 
						

					

					
Scoring rules and output format:
						forms_search/evals/README.md. Our reference runner, run_evals.py, is one example.
